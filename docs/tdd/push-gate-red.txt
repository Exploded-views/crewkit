Reading: every injected git or grep failure let the push through (exit 0): fail-open (a), rev-list
failing in `for c in $(git rev-list ...)`, scanned nothing; fail-open (b), `n=$(git show | grep -Eic)`
came back empty on grep's exit 2 and `(( n > 0 ))` read it as no hits. git show, git grep and
git ls-tree failing, and a pushed sha missing from the repository, failed open the same way.
Two tests are tightenings, not fail-opens: the original had no recorded-sha256 check for gitleaks
(any binary at the path passed), and treated an unreadable exempt file as absent (it gates every
remote, so a clean push passed); both now refuse.

The tests for install, status, --doctor, gate-check, shim and the dispatcher had no code in the
port to fail against (the original has `<remote> <url>` only; the adapter answers 64 to anything
else), so they failed by absence. A first run of the author-name test failed on the original for a
test bug: GIT_AUTHOR_NAME in the environment overrides `-c user.name`; the helper now sets the env.
Order, stated plainly: the hook's fail-closed fixes were written against these failing tests; the
new subcommands (install, status, --doctor, gate-check, shim) were drafted in the same sitting as
their tests, so their RED is by absence only. Their mutants (tests/mutants/push-gate*.json) are
the evidence that each of those tests bites.
